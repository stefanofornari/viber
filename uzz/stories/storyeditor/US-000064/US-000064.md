## US-000064 — UserStory JavaFX Model with Markdown Round-Trip

### User Story

```
AS A Developer
I WANT a UserStory model built on JavaFX properties that can be parsed from and rendered to uzz story markdown
SO THAT I can bind, observe and programmatically manipulate a story without handling markdown myself
```

#### Status
DONE

#### Dependencies
- None

#### Technical Context & Constraints
* **Target System**: Java application, JavaFX properties, own package isolated from the rest of Viber
* **Toolchain / Rules**: Java, JavaFX, Maven, JUnit 5, AssertJ BDD; `uzz/project/coding_standard.md` (fieldName()/fieldName(value) accessors, `Safe` utilities); TDD per `uzz/project/development_framework.md`

#### Notes
1. Fields: ID, title, role, want, so-that, status (`TODO`, `WIP`, `DONE`, `BLOCKED`), dependencies (observable list), technical context, notes, acceptance scenarios (observable list).
2. The markdown format is the one defined in `uzz/skills/kb/references/user_story.md`.
3. Parsing is structural only; no INVEST or Gherkin semantic validation.
4. Unparseable input raises a descriptive exception; it never yields a half-filled story.

### Acceptance Criteria

```gherkin
Scenario: Parse a well-formed story
  Given a markdown text following the uzz user story template
  When the Developer parses it into a UserStory
  Then ID, title, role, want, so-that, status, dependencies, technical context, notes and scenarios are populated

Scenario: Round trip preserves the story
  Given a UserStory parsed from valid markdown
  When it is rendered to markdown and parsed again
  Then the resulting model equals the original

Scenario: Properties are observable
  Given a UserStory with a listener on its title property
  When the title is changed
  Then the listener is notified with the old and new value

Scenario: Malformed markdown is rejected
  Given a markdown text with no "AS A / I WANT / SO THAT" block
  When the Developer parses it
  Then a descriptive parsing error is raised
```
